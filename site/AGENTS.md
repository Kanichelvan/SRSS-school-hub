# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Secure hub implementation decisions

- The product is the **SRSS Digital Hub** (SRSS25 is the launch occasion). The secure hub (`/sign-in`, `/hub/*`) runs on React + Vite with Firebase (Auth, Firestore, Functions, Security Rules) and Google Workspace as the productivity layer. The user chose to keep React + Vite rather than the PRD's Next.js. Setup: `docs/HUB-SETUP.md`; data model: `docs/data-model.md`; requirement status: `docs/requirements.md`.
- `src/auth/permissions.js` is the single source of truth for hub roles (PRD user groups) and the V/C/U/A/R module matrix. Any change must be mirrored in `firestore.rules` / `storage.rules` and pass `npm test` and `npm run test:rules`.
- Roles live only in Firebase custom claims set by `setUserRoles`; access scope lives in server-derived `users/{uid}` (`functions/scope.js`). Per-child records carry `studentId` + `classId`, and hub queries must be constrained so every returned document is readable.
- Hub route metadata (label, module, phase, Google services, screen) lives in `src/hub/routes.js`. Use the shared components in `src/hub/ui.jsx`; the student hub stays deliberately simple (large cards, few choices).
- Human Values are recorded as specific observations, never numeric scores; public showcase needs a moderator and recorded consent; consent records are append-only.
- Hub reads are one-shot (no realtime listeners) to keep Firebase on free allowances.
- Firestore is the system of record for children, guardians, enrolment, attendance, admissions and consent. Applications and consent are hub forms; Google Sheets only receives read-only reports and Google Forms only handles low-risk public intake (user decision, 10 Oct 2026).
- The Silver Jubilee lives at `/about/silver-jubilee` (Architecture v2.0; it grows into a mini-site with its own sub-navigation); the homepage keeps one restrained Silver Jubilee band linking there.
- The Workspace edition is unconfirmed: keep plans edition-neutral until the school confirms (Google for Nonprofits excludes schools).
- Public website images come from the hub image library (Content → Image library): every image needs alt text, and photos showing pupils need the uploader's public-media consent confirmation. Uploads are resized in the browser (max 2,000 px, WebP).
- Any demo role-switching bar is local-demo only (emulators); never ship view switching without sign-in.
- Any set of five — the human values, Rukun Negara principles, SRSS25 themes and similar — uses the SRSS25 mark's petal colours and glossy finish (`--petal-*` tokens and `--petal-rim` in `styles.css`), always mapped Truth red, Right Conduct blue, Peace purple, Love green, Non-violence orange (the Values Garden mapping) (user decision, 10 Oct 2026).
- Role-based application (user decision, 14 Oct 2026): six main roles — Super Administrator (`superAdmin`), School Administrator, Teacher, Parent, Student, Content Editor — with the other roles added to a person as extra responsibilities. Only server functions (`provisionAccount`, `setUserRoles`, `setAccountStatus`) create accounts or change roles; the office may grant family and teacher roles, everything else needs a Super Administrator, and nobody changes their own roles or assigns themselves to a class. Teacher access comes only from active assignments for the current academic year (plus `assignmentKeys` for subject-level checks).
- School master data is managed in the Admin hub with `RecordManager` (`src/hub/manage.jsx`): search, filters, create, edit, archive/restore, validation and “created / last updated by” lines. Nothing is deleted; enrolments and assignments are ended or archived, and the fields that give a record its meaning (class, year, teacher, subject) can't be rewritten.
- School Setup Wizard (user decision, 14 Oct 2026) at `/hub/admin/setup`: nine steps whose status is worked out from real records, with the annual roll-over (copy classes, carry assignments forward, promote pupils, activate the year). Keep it the main way a small office prepares a year.
- Attendance: the active Late (L) button uses an orange metallic gradient (user decision, 14 Oct 2026). Everyone defaults to Present in the unsaved form; a register counts only once submitted (saved in small batches, session marked submitted last); later changes are corrections that need a reason and are recorded. Announcements are internal (public news stays in `newsPosts`), with categories, audiences, drafts, scheduling, expiry, pinning and Drive-link attachments. Portfolio entries never become public themselves — an approved, consented showcase entry is copied without media or surname to `showcaseItems`.
- Large client writes stay in batches of 8 (`commitInChunks`) because security rules may read at most 20 other documents per batch.
- Hub dates are local (Malaysia) calendar dates (`localDate`/`today()` in `src/hub/data.js`), never `toISOString()` on its own.
- Development demo data is fictional and lives in `scripts/demo-data/`; the seed refuses anything but the local emulators.
